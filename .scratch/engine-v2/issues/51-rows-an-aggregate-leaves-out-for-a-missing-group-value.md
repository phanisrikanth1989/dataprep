# 51 - Rows an aggregate leaves out for a missing group value

Status: resolved
Type: grilling

## Question

An aggregate row leaves out every row that has no value in a group column.
The job ends in success and nothing says so. v1 does the same, so v2 follows
it. Should that stay, be told in the log, or change?

Found on 2026-10-07 by the review of
[Say when rows are dropped for a fault](46-say-when-rows-are-dropped-for-a-fault.md),
and then run again here. Ticketed only; for the dev to decide.

## What is known

- The case: file -> aggregate row (group by `dept`, sum of `amount`) ->
  file, with the rows `1;1`, `;2`, `1;3`, `;40`, `2;5`. Both engines write
  `1;4` and `2;5`. The two rows without a `dept` are in no group: 42 of the
  51 in `amount` are gone. No warning; with `--row-counts` the component
  shows NB_LINE 5, OK 2, REJECT 0.
- In v2 it is a filter before the grouping
  (`src/v2/components/aggregate/aggregate_row.py`, where the group keys are
  taken). In v1 it is what pandas does by default: `groupby` drops the rows
  whose key is missing (`src/v1/engine/components/aggregate/aggregate_row.py`,
  the `groupby` call).
- Not known: what Talend's tAggregateRow does with a missing group value.
  If it keeps those rows as a group of their own, v1 and v2 both write less
  than the Talend job did.
- The same kind of thing in a context load: a row with no key is skipped
  without a word, in v1 and in v2. That one loses a setting, not data.
- Telling it should cost little: the engine can now notice rows as they
  pass (ticket 46; 0.04 to 0.08 s at a million rows for a reader's rows,
  not measured for an aggregate).

## To settle

1. **What Talend does.** That decides whether this is a fault of v1's that
   v2 has copied, or the right answer.
2. **If it stays as it is: say it in the log**, as ticket 46 does for a row
   a reader could not read ("2 rows were dropped: no value in the group
   column 'dept'; the first is line 3 of in.csv"), or leave it silent.
3. **If Talend keeps the rows**: whether v2 should, which would make its
   files differ from v1's for such data.

## Answer

Decided on 2026-10-07. The dev's word: "there is a talaxie or some github
repo present where you can see the actual implementation if you want and
then make a decision here".

What Talend does, read in its source: Talaxie `tdi-studio-se`, master at
639d5fd1f776, under `main/plugins/org.talend.designer.components.localprovider/
components/`. A tAggregateRow's code is generated by `tAggregateOut` and
`tAggregateIn`.

- `tAggregateOut_begin.javajet` generates the group key, a class
  `AggOperationStruct_<id>`. Its `hashCode()` adds
  `(this.<column> == null) ? 0 : this.<column>.hashCode()` (line 656), and
  its `equals()` takes two missing values for equal (lines 696 to 700).
- `tAggregateOut_main.javajet` copies the group columns of every row into
  the key (lines 129 to 137) and looks the key up in a `HashMap`, adding it
  when it is new (lines 184 to 222). No row is left out for a missing value.
- `tAggregateIn_main.javajet` hands the key on as it is (line 142).

So in Talend the rows that miss a group value are a group of their own.
v1 loses them, because pandas' `groupby` drops them unless it is told
`dropna=False`. That is a fault of v1's, and v2 had copied it.

Decided: v2 keeps those rows, as Talend does. Being the same as Talend is
the project's first rule, and rows lost without a word are the worst kind
of difference. v2's files now differ from v1's for such data; the README
says so under "Differences from v1".

Built:

- The aggregate no longer leaves those rows out. Their group comes where
  its first row arrives, like any other, and its key is written as nothing.
  Of `1;1`, `;2`, `1;3`, `;40`, `2;5` summed by the first column, v2 writes
  `1;4`, `;42`, `2;5`. With `--row-counts` the component shows NB_LINE 5,
  OK 3.
- Nothing is said in the log: no row is dropped any more.
- Held by tests against v1 run with pandas told to keep such rows (`kept`
  in `tests/v2/components/test_aggregate_row.py`). v1 as it stands is no
  answer key here; told so, it is one for where the group comes, how its
  key is written and what its results are.

Not changed:

- v1. It still loses the rows. One argument would fix it (`dropna=False`
  in the `groupby` of `src/v1/engine/components/aggregate/aggregate_row.py`);
  that is the dev's to order.
- The context load. Talend also skips a row with no key without a word
  (`tContextLoad_main.javajet`: a value is set only `if (tmp_key != null)`),
  so v1 and v2 are as Talend is.
- The order of the groups. Talend writes them in the order of its HashMap
  (`tAggregateIn_begin.javajet`); v1 and v2 in the order their first row
  arrives. That was so before this ticket and is not part of it.
