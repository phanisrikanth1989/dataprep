# 52 - A key missing on both sides of a join or a map lookup

Status: needs-triage
Type: grilling

## Question

In Talend, a row whose join key is missing matches the lookup's row whose
key is missing too. In v2 a missing key matches nothing. Should v2's join
and map lookups do as Talend does?

Raised on 2026-10-07, after
[Rows an aggregate leaves out for a missing group value](51-rows-an-aggregate-leaves-out-for-a-missing-group-value.md)
showed that Talend's aggregate takes a missing value for a value like any
other: its join and its map compare keys the same way. Checked in Talend's
source and run on both engines. Ticketed only; for the dev to decide.

## What is known

Talend's source: Talaxie `tdi-studio-se`, master at 639d5fd1f776.

- Every row class is generated by
  `main/plugins/org.talend.designer.codegen/jet_stub/subprocess_header.javajet`.
  For the key columns of a lookup, its `hashCode()` adds
  `(this.<column> == null) ? 0 : this.<column>.hashCode()` (line 282) and
  its `equals()` takes two missing values for equal (lines 322 to 328).
- Join (`components/tJoin/tJoin_begin.javajet`, `isJoined`): the main row's
  key is copied into a lookup key and looked up in the hash map. There is
  no check for a missing value, so missing matches missing.
- Map (`components/tMap/tMap_main.inc.javajet`, lines 786 to 860 and 957):
  it goes by the type of the lookup's key column. A Java primitive (a number
  or a boolean declared not nullable): a missing value on the main side
  skips the lookup, so no match. Anything else (text, a date, a BigDecimal,
  a nullable number): the key is looked up as it is, missing included.
- Unique row (`components/tUniqRow/tUniqRow_begin.javajet`, `KeyStruct`):
  the same compare, so rows that miss the key are duplicates of each other.

Run on 2026-10-07 with main rows `1;10`, `;20`, `3;30` and lookup rows
`1;ann`, `;nobody`. What the row `;20` gets:

| | key | Talend, by its source | v1 | v2 |
|---|---|---|---|---|
| join | text | nobody | nobody | nobody |
| join | whole number | nobody | the job fails | nothing |
| join | date | nobody | nobody | nothing |
| map lookup | text | nobody | nobody | nobody |
| map lookup | whole number | nobody when the lookup key is nullable, nothing when it is not | nothing | nothing |
| map lookup | date | nobody | nothing | nothing |
| unique row | whole number | the second such row is a duplicate | the same | the same |

- A text key with nothing in the field is the text "" in both engines and
  in Talend, and "" matches "". The difference is for a key that is truly
  missing: a number, a date or a Decimal with nothing in the field, or text
  that went missing earlier in the job (after a join with no match, say).
- It shows only where the lookup itself holds a row with a missing key.
  Then Talend hands that row's columns to every main row that misses the
  key, and under an inner join passes those rows on; v2 hands them nothing,
  and under an inner join turns them away.
- The unique row is as Talend has it. Nothing to do there.
- Not run on Talend itself: the Talend column is read from its source.

## To settle

1. **Join.** Missing matches missing, for every type, as Talend's tJoin
   has it. (Where Talend's lookup key is a primitive and the main value is
   missing, its generated code fails on the row. v2 would need the lookup
   column's declared `nullable` to tell.)
2. **Map lookup.** Talend's rule goes by the lookup key column: nullable,
   or text, date or Decimal, matches; a number or boolean declared not
   nullable never does. v2 takes no notice of a join key's `nullable`
   today ("A missing key never matches").
3. **Against v1.** v2 would then agree with v1 where v1 matches (a join on
   a date key), and differ from it where v1 fails (a join on whole numbers)
   or does not match (map lookups).
4. **Cost.** A Polars join can take missing keys for equal
   (`nulls_equal`); what that costs is to be measured on the payments
   scenario.

Where I lean: do as Talend does in both. Same reason as in ticket 51: the
same as Talend is the first rule, and a row that silently gets no match is
a wrong result nobody is told about.
