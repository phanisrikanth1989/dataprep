# v2 engine as found (charting evidence)

Analysed 2026-10-05, read-only, at commit `cf01691a` on `feature/engine-v2`:
v2 exactly as imported from ETL-AIAgent on 2026-10-04. This is the starting
point the [Engine v2 map](../map.md) was charted from.

Provenance: every item under "Verified findings" was reproduced with the
scripts in `probes/` on one Mac running polars 1.44.2 and Python 3.14.6. The
repo pins `polars>=1.38,<2.0` and Python 3.12+. Findings 13, 14, 19 and 20
depend on Polars' own behaviour and are provisional for the target servers;
the rest are engine logic and do not depend on the Polars version.

## What v2 is

- 8,351 lines under `src/v2`. Config is a Pydantic `JobConfig`: typed context
  variables, components (`id`, `type`, free `config` dict), flows with named
  ports, optional triggers.
- Components pass Polars `LazyFrame`s. The engine collects only at barriers:
  sinks, the python components, utility components, and anything that returns
  two outputs. With triggers, flow-connected groups of components become
  "stages" (now called subjobs) ordered by a trigger graph.
- Expressions are a hand-written tokenizer, parser and compiler for a custom
  language of about 60 functions, plus routines (Python files auto-loaded and
  called as `Name.func(...)`).
- 18 component classes under 25 registered names. No Java bridge, no
  globalMap, no exception hierarchy, no command line, no v1/v2 router.
- `talend_to_v2` handles 16 Talend type names and marks Java expressions for
  manual rewrite. `v1_to_v2` drops triggers and iterate flows that the engine
  supports.

Baseline on this Mac: `tests/v2` 898 passed, 11 skipped (all benchmark tests),
0 failed. The two converter suites have 9 failures, all stale references to
renamed modules and types. `src/v2` and both v2 converters are outside the
coverage gate. The standard's doc-validation gate is not wired here (no
pre-commit config, no CI workflow). Benchmarks were not run.

## The rules it ran on, and what was decided

| # | Rule as found | Decided 2026-10-05 |
|---|---|---|
| R1 | Performance first, capability second: what cannot be a lazy Polars operation is out | Stays |
| R2 | Lazy everywhere: components never collect, the engine collects at barriers | Stays |
| R3 | One custom expression language; Java never executed | Replaced: expressions are Python, translated once to Polars |
| R4 | No Python callbacks in components except the three python components | Stays; may be extended later if a real need appears |
| R5 | Explicit schema, never inferred; seven logical types; decimals held as strings | Stays (the decimal representation is open in Types, nulls and schemas) |
| R6 | Config is a free dict; each component hand-checks it; unknown keys pass | Replaced: declared config keys, refusal at load |
| R7 | Row errors go to a reject output when `die_on_error` is false; an error is "this value became null" | Stays |
| R8 | Context doubles as globalMap; iterate and file-list values are injected as `{component_id}_KEY` | Stays |
| R9 | Five deliverables per component: runtime, Talend converter, doc, golden-case tests, benchmark within 10% of raw Polars | Revised: see the map's Notes |

## Verified findings

Rows lost or reordered while the job reports `success`:

1. Two flows into one component on the default port: the second replaces the
   first. A `unite` of files A and B wrote only B.
2. One component sending two outputs to the same target (filter `main` and
   `reject` into a `unite`): only one arrives.
3. A flow naming a port the source does not emit is not an error. `uniq_row`
   emits `unique`; a default flow asks for `main`; the sink writes no file.
4. `unite` row order changes between runs, because inputs are walked through a
   Python `set`: five different orders across twelve hash seeds.
5. `filter_rows` with a reject output drops rows whose condition is null:
   4 rows in, 2 to main, 1 to reject.
6. In an iterate loop, a source feeding two sinks feeds the second one only on
   the first iteration (three files: first sink got 1, 2, 3; second got 1).
7. Nested iterate runs the inner body one extra time per outer pass (6 runs
   where 4 are expected).
8. In a flat job (no triggers) that declares no context variables, iterate
   values never reach the components: `context or {}` gives each component a
   private empty dict.
9. Without triggers, `context_load` runs in alphabetical-id order relative to
   everything else, and a filter compiled at construction keeps the old
   context value (kept rows 5 and 500 with a loaded threshold of 100).

Expression language:

10. The parser ignores everything after the first complete expression:
    `amount > 100 garbage here` compiles as `amount > 100`, and `foo(1, 2)`
    compiles as the column `foo`.
11. `x == null` and `x != null` are never true; only `ISNULL(x)` works.
12. Twelve function names are recognised but not implemented (`case`, `cast`,
    `collect_list`, `collect_set`, `count_distinct`, `decode`, `pad_left`,
    `pad_right`, `parse_datetime`, `regexp_match`, `today`, `when`).
    `MIN(a, b)` returns the column-wide minimum.
13. Arithmetic follows Polars: `7 / 2` is 3.5, `-7 % 2` is 1, `null + 'x'` is
    null, `'n=' + 7` is an error, `x / 0` is infinity. Under Python
    expressions most of this is correct Python and no longer a defect.
14. A scalar routine inside an expression produces an `Object` column that the
    CSV writer rejects, as does a string function such as `UPPER` wrapped
    around it.
15. In `map`, an output expression of `null` or `true` is read as a column
    name and fails.
16. Trigger conditions are a third syntax: `context.n > 0` and `&&` are
    rejected, a bare word counts as true, and `globalMap.get(...)` cannot be
    written.

Types and file I/O:

17. Decimal columns are strings and `TO_DECIMAL` is float64: `10.10 * 3` is
    written as `30.299999999999997`.
18. Talend-style type names (`id_Integer`) with `die_on_error: false` stay
    strings and reject nothing.
19. On CSV read an empty field becomes null while `""` becomes an empty
    string; the text `NaN` or `nan` in a string column becomes null.
20. `file_input_full_row` fails on a line that starts with a quoted segment.
21. In `file_input_excel`, a real date cell fails unless the column's pattern
    happens to be ISO.
22. In `map`, a lookup's key column cannot be referenced (`l1.k` is not
    found), and two inner-join lookups with a lookup-reject output fail with
    "schema lengths differ".

Engine and observability:

23. Sinks report zero rows, so the job summary's "rows written" counts other
    components.
24. A bad value in a lazily read source fails at the sink; the error names no
    component and the source is recorded as completed.
25. When a subjob fails with no handler, independent subjobs still run.
26. A misspelled config key (`delimeter`) passes validation and the default is
    used; an unresolved `${context.x}` stays in the path as literal text.

Also seen, not probed: `python_dataframe`'s `routines` namespace is never
connected (`set_routine_manager` has no caller); `file_input_full_row`
documents `row_separator` and never reads it.

## v1 job configs versus v2 as found

| Meaning | v1 job config | v2 as found |
|---|---|---|
| Job name | `job_name` | `name` |
| Flow | `{name, from, to, type}` | `{source, output, target, input}` |
| Trigger | `{type: OnSubjobOk, from, to}` | `{type: on_success, source, target}` |
| Context | grouped: `{"Default": {var: {value, type}}}` plus `default_context` | flat: `{var: {value, type}}` |
| Schema | beside config: `schema: {input, output}` | inside config: `config.schema` |
| Component type | `FileInputDelimited` (also `tFileInputDelimited`) | `file_input_delimited` |
| File path | `filepath` | `path` |
| Field separator | `fieldseparator`, default `;` | `delimiter`, default `,` |
| Header | `header_rows: 1` | `has_header: true`, `skip_rows` |
| Encoding default | `ISO-8859-15` | `utf8` (the only one accepted) |
| File input `die_on_error` default | `false` | `true` |
| Filter | `conditions: [{column, operator, function, value}]`, `logical_op` | `condition: "<expression>"` |
| Aggregate | `groupbys`, `operations` | `group_by`, `aggregations` |
| Sort | `criteria: [{column, sort_type, order}]` | `columns: [{name, order}]` |
| Schema types | `str`, `int`, `float`, `bool`, `datetime`, `Decimal` | `string`, `integer`, `float`, `boolean`, `date`, `datetime`, `decimal` |

`agents/schemas/config-surfaces.md` is the code-verified list of v1 config
keys and defaults for eight components. `docs/JOB_CONFIGURATION_SCHEMA.md`
describes a different, older outer shape and does not match what the v1
converter emits.

Facts from the 37 v1 job configs in `tests/talend_xml_samples/converted_jsons/`
(converter fixtures, not production jobs):

- Top-level keys, all 37: `job_name`, `job_type`, `default_context`, `context`,
  `components`, `flows`, `triggers`, `subjobs`, `java_config`, `_validation`,
  `_needs_review`.
- Component keys, all 125: `id`, `type`, `original_type`, `position`, `config`,
  `schema`, `inputs`, `outputs`.
- Flow types: flow 71, reject 3, iterate 2, filter 1, unique 1, duplicate 1.
  Trigger types: OnSubjobOk 6, OnComponentOk 2.
- Schema column keys: `name`, `type`, `nullable`, `key`, `length`, `precision`,
  `date_pattern`.
- 41 of 1,629 config strings start with `{{java}}`: Map 32, RowGenerator 7,
  FilterRows 1, SetGlobalVar 1.
- `encoding` is `ISO-8859-15` on 36 of the 38 delimited file components.
- Most common component types: LogRow 34, FileInputDelimited 31,
  FileOutputDelimited 7, Map 6. No job uses PyMap.

## How v1 writes Python expressions

v1's `PyMap` (`src/v1/engine/components/transform/py_map.py`) takes the same
config shape as `Map` with plain Python expressions and no `{{java}}` prefix:
`row1['price'] * 1.05`, `row1.price * 1.05`,
`re.sub(r'\s+', '_', row1['name'])`. It evaluates them with `eval`, once per
row, in a namespace of `row1`, `row2`, ... (dicts with attribute access),
`Var`, `context`, `globalMap`, `pd`, `np`, `re`, `datetime`, `Decimal`,
`json`, `math` and a set of safe builtins. v1 trigger conditions are evaluated
as Python too (`src/v1/engine/trigger_manager.py`). v1's FilterRows advanced
condition accepts Java only.

v1's `PythonDataFrameComponent` takes `python_code` and `output_columns`; the
code receives a pandas DataFrame named `df` and changes it in place. v2 as
found takes `code`, hands over a Polars DataFrame (pandas on request) and
expects the code to set `output_df`.
